# Releasing

Push a version tag to create a draft GitHub Release. Review the generated notes,
then publish the release to start PyPI publication. GitHub Releases also serves
as the project changelog.

## Required Local Checks

From a prepared development checkout, run validation and build before tagging:

```bash
npm --prefix tests/typescript ci
npm --prefix editors/vscode ci
pdm run validate
pdm run smoke:cli
pdm build
pdm run package-check
npm --prefix editors/vscode test
npm --prefix editors/vscode run package
pdm run pytest tests/offline/tooling/test_language_server.py
```

`pdm run validate` runs Ruff, strict mypy, docs-check, the offline Python tests,
and editor tests. Live OpenAI tests remain opt-in and are not part of the release gate
unless the release changes live adapter behavior.

## Process

1. Choose the next semantic version tag.
2. Replace `vX.Y.Z` with that tag, then create and push it:

```bash
git tag vX.Y.Z
git push origin vX.Y.Z
```

3. Wait for every validation job in `Create Draft Release` to succeed and for
   the workflow to create the draft.
4. Review the drafted GitHub Release generated by
   `btfranklin/release-notes-scribe`.
5. Confirm the draft release includes
   `contract4agents-vscode-X.Y.Z.vsix` as a release asset.
6. Publish the GitHub Release.
7. Confirm the `Upload Python Package` workflow completes.
8. Download the published VSIX into temporary VS Code state, install it, and
   confirm the reported extension version matches the release tag:

```bash
tmpdir="$(mktemp -d)"
gh release download vX.Y.Z --repo btfranklin/contract4agents \
  --pattern "contract4agents-vscode-X.Y.Z.vsix" --dir "$tmpdir"
code --user-data-dir "$tmpdir/user-data" \
  --extensions-dir "$tmpdir/extensions" \
  --install-extension "$tmpdir/contract4agents-vscode-X.Y.Z.vsix" --force
code --user-data-dir "$tmpdir/user-data" \
  --extensions-dir "$tmpdir/extensions" \
  --list-extensions --show-versions
```

## Workflow Boundaries

- `.github/workflows/python-package.yml` validates pushes and pull requests
  across Python 3.11, 3.12, 3.13, and 3.14. It is also callable by draft
  preparation and runs lint, types, docs, offline tests, CLI smoke tests,
  package builds, and package contents checks.
- `.github/workflows/vscode-extension.yml` tests the real Python language-server
  boundary, tests the extension, and builds the VSIX on pushes and pull
  requests. Draft preparation calls the same workflow, which sets the extension
  version from the tag before testing and packaging the release asset.
- `.github/workflows/create-draft-release.yml` runs on pushed `v*.*.*` tags.
  It calls both ordinary CI workflows for the exact tag. Only after both pass
  does it create the actual draft with `btfranklin/release-notes-scribe` and
  attach the validated, version-matched VSIX from that workflow run.
- `.github/workflows/python-publish.yml` runs when a GitHub Release is
  published. It trusts draft preparation, checks out the release tag with full
  history, rebuilds the Python archives, and publishes through PyPI Trusted
  Publishing. It does not repeat tests, lint, type checks, documentation checks,
  CLI smoke tests, or package validation. Its workflow identity and `release`
  environment remain the trusted-publisher boundary.
- Versioning is SCM-derived through the PDM configuration in `pyproject.toml`.

The supported validated-draft path is: push the version tag, wait for all checks
and the generated draft, review the notes and VSIX asset, then click Publish.
Creating a draft manually in GitHub does not trigger the tag workflows and does
not establish that it passed validation. Do not publish before the tag workflow
completes. Publication does not generate release notes or recover prior runs;
it rebuilds the Python packages from the same release tag. Live provider tests
remain opt-in under the [validation guidance](quality/validation.md).
